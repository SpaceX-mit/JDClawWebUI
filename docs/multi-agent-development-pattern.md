# 多 Agent 并行开发模式

> 本文档总结 JDClawWebUI 项目中实践的多 Agent 并行开发方法论。
> 该模式适用于由 AI Coding Agent 执行的中大型前端项目开发。

---

## 1. 核心原理

多 Agent 并行开发的核心思想：

- **任务拆分**: 将一个大的开发阶段拆分为多个独立的工作流（Stream）
- **并行执行**: 每个 Stream 由一个独立的 AI Agent 同时执行，互不阻塞
- **冲突隔离**: 通过文件所有权机制确保不同 Stream 不会修改同一文件
- **统一集成**: 所有并行 Stream 完成后，由集成阶段统一合并到核心文件

```
┌─────────────┐
│  任务规划     │
│  (拆分 Stream) │
└──────┬──────┘
       │
  ┌────┴────┐
  ▼         ▼
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│ A   │ │ B   │ │ C   │ │ D   │  ← 并行执行
└──┬──┘ └──┬──┘ └──┬──┘ └──┬──┘
   └───┬───┴───┬───┴───┬───┘
       ▼
┌─────────────┐
│  集成阶段     │
│  (合并到核心)  │
└─────────────┘
```

---

## 2. 拆分策略

### 按组件/文件边界拆分

每个 Stream 独占修改特定文件，这是避免冲突的关键：

- **新建文件可完全并行**: 不同 Stream 创建不同的新文件，零冲突风险
- **共享文件只允许追加（append-only）**: 如 `types/index.ts`，只允许在文件末尾追加新类型定义
- **核心文件留给集成阶段**: 如 `jd-app.ts` 是状态管理中枢，多个 Stream 都需要修改它，因此统一留给集成阶段处理

### 拆分原则

1. **高内聚**: 一个 Stream 内的任务应该紧密相关（如 "Session CRUD" 包含右键菜单 + 侧边栏修改 + API 扩展）
2. **低耦合**: Stream 之间尽量不依赖对方的产出
3. **均衡负载**: 每个 Stream 的工作量大致相当，避免某个 Stream 成为瓶颈
4. **明确边界**: 每个 Stream 的文件列表必须在启动前确定

### 实际拆分示例（P0 阶段）

```
Stream A（基础设施）: 创建 jd-toast.ts, jd-confirm-dialog.ts
Stream B（Chat 增强）: 修改 jd-chat-view.ts
Stream C（Session CRUD）: 创建 jd-context-menu.ts, 修改 jd-sidebar.ts, 追加 gateway.ts
Stream D（本地设置）: 创建 settings.ts
集成: 修改 jd-app.ts
```

## 3. 文件冲突矩阵

在启动并行开发前，必须绘制文件冲突矩阵，确保同一文件同一时间只有一个 Stream 修改。

### 矩阵标注规则

| 标记 | 含义 | 冲突风险 |
|------|------|----------|
| 创建 | 新建文件 | 无（文件不存在） |
| 修改 | 修改已有文件 | 高（必须独占） |
| 追加 | 仅在文件末尾追加 | 低（但需协调） |
| - | 不涉及 | 无 |

### P1 阶段冲突矩阵示例

| 文件 | Stream A | Stream B | Stream C | Stream D | Stream E | 集成 |
|------|----------|----------|----------|----------|----------|------|
| `jd-tool-card.ts` | 创建 | - | - | - | - | - |
| `jd-chat-view.ts` | - | 修改 | - | - | - | - |
| `router.ts` | - | - | 创建 | - | - | - |
| `jd-slash-menu.ts` | - | - | - | 创建 | - | - |
| `styles.css` | - | - | - | - | 修改 | - |
| `jd-app.ts` | - | - | - | - | - | 修改 |
| `types/index.ts` | 追加 | - | - | - | - | - |

**关键规则**: 每一列（文件）中，"修改" 标记最多只能出现一次。如果多个 Stream 都需要修改同一文件，必须重新拆分任务或将该文件的修改移到集成阶段。

## 4. Agent 提示词编写要点

提示词质量直接决定 Agent 产出质量。以下是关键要素：

### 4.1 提供完整的项目上下文

```markdown
## 项目上下文
- 技术栈: Lit 3.x + TypeScript 5.x + Vite
- 组件基类: LitElement，使用装饰器 @customElement, @property, @state
- 样式方案: CSS 变量（--jd-* 前缀），组件内 static styles
- 构建验证: npm run typecheck && npm run build
```

### 4.2 明确指定文件路径

```markdown
## 你需要操作的文件
- 创建: src/components/jd-toast.ts
- 创建: src/components/jd-confirm-dialog.ts
- 不要修改其他文件
```

### 4.3 给出具体的类型定义和接口

```typescript
// 在提示词中直接提供接口定义
export interface ToastOptions {
  type: 'success' | 'error' | 'warning' | 'info';
  message: string;
  duration?: number; // 默认 3000ms
}

// 提供组件的公共 API
export class JDToast extends LitElement {
  static show(options: ToastOptions): void;
  static success(message: string): void;
  static error(message: string): void;
}
```

### 4.4 包含 CSS 变量和设计规范

```markdown
## 设计规范
- 圆角: var(--jd-radius, 8px)
- 阴影: var(--jd-shadow)
- 主色: var(--jd-primary)
- 危险色: var(--jd-danger)
- 动画时长: 200ms ease
- Toast 堆叠间距: 8px
- Toast 最大宽度: 400px
```

### 4.5 要求运行验证

```markdown
## 完成标准
1. 代码通过 TypeScript 类型检查: npm run typecheck
2. 构建成功: npm run build
3. 组件已在 customElements 注册
4. 导出类型供其他组件使用
```

### 4.6 提示词模板

```markdown
# Stream [X] — [名称]

## 项目上下文
[技术栈、文件结构、现有代码概述]

## 当前文件内容
[粘贴相关文件的完整内容，让 Agent 了解现有代码]

## 任务目标
[清晰描述要实现的功能]

## 要操作的文件
- 创建: [文件路径]
- 修改: [文件路径]（说明修改范围）

## 类型定义
[提供接口和类型]

## 设计规范
[CSS 变量、尺寸、颜色]

## 完成标准
[typecheck、build、功能验证点]

## 注意事项
- 不要修改 [文件列表] — 这些文件由其他 Stream 负责
- [其他约束]
```

## 5. 集成阶段

集成阶段是整个并行开发流程的关键收尾环节。

### 5.1 前置条件

- 所有并行 Stream 已完成并通过各自的 typecheck
- 所有新建文件已就位
- 共享文件的追加内容已合并

### 5.2 集成步骤

1. **读取所有变更**: 主 Agent 读取每个 Stream 产出的所有文件，理解各组件的 API 和事件
2. **修改核心文件**: 统一修改 `jd-app.ts` 等核心文件
   - 导入所有新组件
   - 在 render 方法中引用新组件
   - 绑定事件处理函数
   - 连接数据流（props 传递、事件监听）
3. **处理交叉依赖**: 解决 Stream 之间的间接依赖（如 Toast 被多个组件使用）
4. **最终验证**:

```bash
# 类型检查
npm run typecheck

# 构建验证
npm run build

# 确认无报错
echo $?  # 应输出 0
```

### 5.3 集成阶段的提示词要点

```markdown
# 集成阶段

## 前置产出
以下文件已由并行 Stream 创建/修改：
- [列出所有 Stream 的产出文件及其公共 API]

## 你需要修改的文件
- src/components/jd-app.ts

## 集成任务
1. 导入以下组件: [组件列表]
2. 在 render() 中添加: [组件标签]
3. 绑定事件: [事件名 → 处理函数]
4. 传递数据: [props 映射]

## 验证
npm run typecheck && npm run build
```

## 6. 实践经验

### 最佳 Stream 数量

**4-5 个并行 Stream 是最佳数量。**

- 少于 3 个: 并行收益不明显，不如串行开发
- 4-5 个: 并行效率最高，冲突可控
- 超过 6 个: 文件冲突矩阵变得复杂，集成阶段工作量激增

### 集成阶段占比

集成阶段通常占总工作量的 **20-30%**。

这个比例看似不低，但考虑到并行阶段节省的时间，整体效率仍然显著优于串行开发。以 P1 阶段为例：

```
串行开发: Stream A + B + C + D + E + 集成 = 6 个单位时间
并行开发: max(A, B, C, D, E) + 集成 = 1 + 0.3 ≈ 1.3 个单位时间
加速比: 约 4.6x
```

### 提示词精确度与返工率

| 提示词质量 | 返工率 | 典型问题 |
|------------|--------|----------|
| 高（含完整上下文 + 类型 + 设计规范） | < 5% | 几乎无需返工 |
| 中（含上下文，缺少类型定义） | 15-25% | 类型不匹配，需手动修正 |
| 低（仅描述功能需求） | 40-60% | 风格不一致、API 不兼容、缺少错误处理 |

### 先读后写原则

**启动 Agent 前，必须先读取所有相关文件。**

这包括：
- 要修改的文件的完整内容
- 相关的类型定义文件
- 设计规范文档
- 已有组件的代码（了解项目风格）

将这些内容直接粘贴到提示词中，而不是让 Agent 自己去读取。这样可以：
- 减少 Agent 的探索时间
- 确保 Agent 看到的是最新版本
- 避免 Agent 读错文件或遗漏关键信息

### 错误处理策略

当某个 Stream 的 Agent 产出不符合预期时：

1. **小问题（类型错误、样式偏差）**: 在集成阶段由主 Agent 直接修复
2. **中等问题（API 不兼容）**: 重新运行该 Stream 的 Agent，提供更精确的提示词
3. **大问题（方向错误）**: 重新拆分任务，可能需要调整 Stream 边界

### 适用场景

多 Agent 并行开发模式最适合：

- 组件化前端项目（天然的文件边界）
- 新功能开发（大量新建文件，冲突少）
- 有明确设计规范的项目（Agent 产出一致性高）

不太适合：

- 深度重构（大量文件交叉修改）
- 算法密集型任务（难以按文件拆分）
- 缺少类型系统的项目（集成时难以验证兼容性）
